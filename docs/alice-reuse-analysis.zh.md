# 白艾莉 Alice：心动伴侣可复用设计对照

日期：2026-09-18。对照本地版本：`cb6f5e5`。

## 范围与判断

研究对象是洛小山／米羊的[白艾莉 Alice](https://alice.miyang.cn/)，公开资料为 [Alice_methodology](https://github.com/itshen/Alice_methodology)。本次阅读官方方法论文档并静态核查心动伴侣代码，没有安装、运行或验证 Alice 客户端，也没有修改本项目运行逻辑。该仓库公开的是方法论，不能据此声称已获得完整产品源码。

关键假设：用户希望把共性设计用于当前心动伴侣；本轮交付调研和实施建议，尚未决定功能范围。

最值得迁移的方向：让角色保持可辨认的身份，并用真实的共同经历改变之后的相处。助手与伴侣都依赖连续性，但前者主要累积工作默契，后者主要累积相处默契。

## 可迁移的机制

| 机制 | Alice 公开设计 | 心动伴侣的迁移建议 |
| --- | --- | --- |
| 稳定身份 | 设定集、受保护人格区、独立的可变偏好区 | 创作者维护角色核心；自动学习仅更新相处习惯。正常的角色编辑仍允许用户修改身份 |
| 分工明确的记忆 | 上下文与长期记忆分开；不同信息采用不同注入方式 | 区分稳定偏好、共同事件、待兑现约定；结合当前话题召回 |
| 有边界的成长 | 反思只改允许范围，变更可以回退；进化提案先呈现再执行 | 学会“难过时先听、不急着提建议”，保留来源、变更记录和撤销能力 |
| 轻量的人情味 | 正式回应之外有转场旁白 | 陪伴对话保留自然小动作或短旁白，低频出现；不要每次套同一动作 |

来源：[活人感设计](https://github.com/itshen/Alice_methodology/blob/main/chapters/16-alive-agent.md)、[上下文与记忆](https://github.com/itshen/Alice_methodology/blob/main/chapters/05-context-memory.md)、[提示词工程](https://github.com/itshen/Alice_methodology/blob/main/chapters/14-prompts.md)、[自我进化](https://github.com/itshen/Alice_methodology/blob/main/chapters/10-self-evolution.md)。上表是对公开设计的归纳及本项目建议，不代表运行效果已经验证。

## 当前项目已有基础与具体缺口

1. **人设已经相当丰富。** `src/services/characterPromptArchitectureService.ts` 包含场景、语气、不同心情的表现、示例对话和关键词触发的背景信息。优先检验这些设定在长对话中的一致性，再考虑增加背景篇幅。
2. **记忆已有用户控制和来源字段。** `src/types/index.ts` 定义来源消息、置信度及 active／locked／superseded 状态；`chatStore.ts` 支持编辑和删除。`ChatScreen.tsx` 在角色回复后调用长期记忆判断。可以沿用这些基础，避免另建一套不兼容的存储。
3. **记忆召回以新旧为主。** `src/services/aiService.ts` 的 `buildSystemMessage` 在非全量模式使用 `activeMemories.slice(-8)`。较早的重要约定、锁定记忆也可能不进入上下文。建议改为预算内的相关性选择，并优先覆盖用户明确要求长期遵守的偏好；首版可用标签、关键词、重要度和时间，不急于接向量库。
4. **长期保存存在硬截断。** `src/store/chatStore.ts` 的 `addMemory` 使用 `.slice(-100)`，没有单独保护 locked 条目；关系事件也有 100 条限制。它会从当前角色的对应列表移除早期条目。是否还可从其他备份恢复需要另外审计，不能直接认定已经不可恢复。检索窗口限制应与永久保存分离。
5. **主动开场缺少共同经历。** `generateDailyGreeting` 调用 `buildSystemMessage` 时使用 `DISABLED_MEMORY_CONFIG` 和空历史；通知服务使用预写文案。可先在用户主动进入聊天时，按授权与时间召回一个未完成约定，验证自然程度，再考虑系统通知。
6. **日记已有事实底座。** `diaryService.ts` 从实际消息摘取内容，空白日不编造经历。以后可增加带来源的角色视角总结，但不能把生成的旁白重新当作真实发生过的共同事件。
7. **人设版本可以复用。** `characterVersionService.ts` 将角色定义快照与运行中的角色数据分开。未来的相处习惯应单独版本化，撤销习惯不应回退或覆盖聊天、日记和记忆。

以上均为当前代码静态观察，尚未进行设备或模型行为测试。

## 建议的第一轮：让一句话在后来的相处里生效

示例输入：用户说“我心情不好的时候，先听我说，别急着给建议。”

预期链路：记录这条明确偏好及来源 → 按现有记忆设置保存／确认 → 多轮或重启后遇到相关场景时召回 → 角色保持自己的语气，调整回应方式 → 用户能修正或撤销。

示例输出，仅用于说明目标：

> 鹿芽：“诶，今天像是有点难熬。我先听你说，你想吐槽哪一段？”

这里要验收的是行为变化；不要求模型背出固定台词，也不要求反复声明“我记得你”。

实施顺序：

1. 审计长期记忆与关系事件的保存上限，制定保留／归档与兼容方案。
2. 给现有记忆增加只读的选择层，替换“最近 8 条”的单一策略；保留原始存储和旧记录可读性。
3. 让主聊天和进入聊天时的问候共用同一份已确认事实与偏好。
4. 有实际收益后，再引入低频的相处习惯提案及独立撤销机制。

不建议首轮引入：自动改应用代码、完整桌面工具权限、大量人格化子 Agent、照搬五层存储体系。这些能力目前没有直接服务于上述验收目标。角色自身的虚构日常若后续加入，应明确归入角色设定，与用户真实经历分开。
