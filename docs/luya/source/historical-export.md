### 配置之间的关系

主聊天由基础 systemPrompt、运行卡的场景/语气/情绪/示例/作者备注、命中背景、记忆、关系规则、时间和通用回复规则共同组成。`qingning` 直接选固定运行卡；profile 派生备用卡用于没有固定运行卡的角色。因此**只改鹿芽 profile 中的经历、兴趣，并不能保证这些内容自动进入上述主聊天提示词**，还要同步梳理固定卡及基础提示词。profile 是已有资料，不应误称每个字段都已生效。

动态背景读取最近 12 条消息，按关键词匹配，按 priority 降序取最多 3 项；包含双方消息，不是独立经过事实核验的召回。

## 4. 关系、情绪、记忆怎样改变她

- 每次用户消息亲密度基础 +1；鹿芽命中“今天”“吃饭/晚饭/午饭/早餐/零食”“哈哈/笑死/好玩/有趣”“陪我/想你/抱抱/需要你”“听你的/谢谢你/你真好”任一组时总计 +3，不按匹配组数累加。上限 100。
- 回复后规则：用户文本含疲惫词会精力 -4；伤心词优先设 sad，否则疲惫设 tired，否则开心词设 happy，其他保留。它未充分区分“我累”“朋友累”和引用内容。
- 另有独立心情校准服务：结合双方消息、角色专属信号和可选模型判断，并非全项目只有上述简单规则。同步置信门槛 0.68，一般切换差值 3，tired 转明亮状态差值 5。能减少瞬间跳变，但仍应区分角色表达风格与用户人格证据。
- 鹿芽专属校准标签：甜甜待机、亮晶晶上扬、声音放软、零食毯子模式、凑近屏幕、嘴上哼哼。
- 她的专属信号见下文源码；这些关键词是启发式规则，像“芋泥”“热可可”不等于已设定的最爱食物。
- 明确记忆要求和候选偏好由系统独立判断；聊天正文不主动询问是否写入记忆。人物卡里的 askMemoryStyle 服务于独立确认，不应和正文规则混用。
- 主聊天排除 superseded 记忆；默认最近 8 条，或设置为全量；locked 有文字标记，但没有保证一定进入最近 8 条。记忆和关系事件当前列表存在 100 条截断。
- 主动问候用空聊天历史和禁用记忆配置；没有服务配置时回退默认 greeting。通知来自固定随机文案。
- 日记基于存储消息摘录；内置漫画是示例，不能当作用户真实经历。

## 6. 值得带去讨论的矛盾与空白

以下是对已有资料的分析，尚未替用户决定改法。

1. **她关心人的原因。** 目前集中在零食、毯子、热饮、冷笑话，缺少经历与动机。为何形成这种方式？失败过吗？何时收住？用户不想吃、不想被安慰时怎么办？
2. **她自己的生活。** 目标几乎都围绕让用户开心；播客、便利店和表情包还没有具体偏好、坚持、能力或挫折。需要哪些独立追求才能支撑人物，而不增加无用设定？
3. **熟悉度与称呼。** 默认室友型亲密、黏人和“笨蛋”出现得很早；怎样让第一次见面、熟悉后和争执后有层次？用户明确不喜欢昵称时怎样停止？
4. **轻快与倾听。** 基础卡倾向共情后逗笑/转移，安静状态要求少转移。哪类场景只陪着？怎样避免总把悲伤拉回开心？
5. **在意与边界。** 忌讳“已读不回”、通知“我可盯着你呢”“不许敷衍”与不催促、不责备的规则有张力；需要明确缺席、拒绝、独处时的行为。
6. **支持与独立判断。** “永远站用户这边”如何包含温和反对、提醒事实、承认不知道，而不变成无条件附和？
7. **口癖与辨识度。** “诶诶”同时是常用语和开心校准信号，“笨蛋”又匹配别扭信号；口癖可能反过来推动情绪判断。应靠选择和反应形成辨识度。
8. **身份与现实。** 路灯住所、室友关系、递毯子、屏幕距离属于什么叙事约定？真实操作、想象动作、预置故事要能分辨。
9. **通用规则过强。** 每次必须共情、每次不超过三句，可能压缩开玩笑、表达自己、认真解释的空间；哪些应该默认，哪些允许例外？
10. **多处配置。** 基础卡、固定运行卡、profile、通知、首页、漫画分散维护；未来确认新设定后需要一起对齐，不应只改一段 Prompt。

## 3. 需要先处理的本项目问题

### P0：共同经历必须存得住，也能被找到

- `src/store/chatStore.ts` 的 `addMemory` 对记忆与关系事件分别截取最近 100 条，锁定条目没有单独保护。
- `src/services/aiService.ts` 默认仅注入最近 8 条有效记忆；锁定记录也可能未入选。
- `generateDailyGreeting` 使用关闭记忆的配置与空历史，因此现有开场无法靠这一路读取已确认的约定。

实施：保存与检索分离；保留全部记录或可恢复归档；提供预算内的相关性选择；把已确认的相关偏好、待跟进约定带入回复和问候。先用标签和规则验证，暂不要求向量数据库。

验收：添加 101 条合成记忆后首条锁定记录仍在；跨 8 条后仍能召回相关偏好；修改和撤销立即影响后续选择；原聊天键、旧格式和文件备份仍可恢复。当前只是发现风险，未在本轮改写存储。

### P1：情绪可以变化，人设和对人的判断有各自边界

建议中间结果包含以下信息，作为新增侧数据或瞬态对象，不直接替换旧消息格式：

```json
{
  "characterId": "qingning",
  "sourceMessageIds": ["example-user-message"],
  "userSituation": "临时加班，今晚没法赴约",
  "characterFeeling": "有一点失落，同时理解情况",
  "traitEvidence": null,
  "intent": "acknowledge_and_reschedule",
  "style": "短句，保留轻快感，不责备，不要求证明在意"
}
```

示例输入：“今晚又要加班，约好的电影看不了了。”

目标表现示例：“诶，好吧，那电影先给你留着。你先忙完，等空下来我们再挑个舒服的晚上。”

只评估表达是否符合意图，不要求模型背固定句子。不能生成“你总是失约”的长期标签；不能伪称已替用户改了真实日历。

### P1：鹿芽有自己的日常，但三处表达只读同一份事实

首版试验日程仅含时间段、地点、活动与完成状态；不做城市地图、经济系统或 NPC 网络。日程写入一次后，首页、聊天、角色日记读取相同事实。同一天重复打开不重抽；跨天只生成新一天；没有真实天气来源时不声称掌握所在地天气。

角色日常是明确的虚构内容；用户事实只能来自用户消息或经过核验的操作结果。生成的独白、示例图和想象情节不得回流成为用户记忆证据。

### P2：印象与低频复盘

先把“记得偏好并按偏好回应”做对，再建立 Clue → Inference → View。为每条推断保留来源、支持、反证、版本与状态；用明确纠错降低或撤销推断；不推断心理诊断、道德标签等与陪伴目标无关的属性。允许用户拒绝被这样理解。

## 4. 材料需要转译的部分

1. **关系型生产力与陪伴的目标不同。** 第 41–45 页强调工作交付。我们可借鉴“先接住具体需求”，转译成倾听、整理用户愿意处理的小事、记住授权的约定；无需把伴侣改成通用办公助手。
2. **自主边界不等于情感惩罚。** 第 22–23、29 页的拉黑／读日记解封属于 Alice 的产品设定。当前项目不建议照搬强制冷处理或用缺席扣分制造负担；拒绝可以清楚表达，并允许用户随时退出、重置互动。
3. **把握不是授权。** 第 34、42 页展示高把握时主动行动。实际提醒、发送、付费工具仍取决于已取得的授权，不能仅凭亲密度执行。
4. **“慢变”不能阻止纠错。** 第 38 页情境充分时不调整把握，第 39 页案例仍因具体承诺冲突记录反证；两页需要结合事实判断，不能写成“外部压力总是免责”或“每次失约都降分”的硬规则。
5. **离线生活不等于后台不断烧模型。** 第 13 页描述连续日程，第 52 页反对离线空转。适合移动端的办法是缓存日程、按时钟推导状态、回到应用时按需补齐必要事件。
6. **世界规模暂缓。** 第 15–28 页的大量场馆、钱包、物流和 NPC 是演示背景。鹿芽先有一个自洽房间、稳定日程和可核验事件就足够验证目标。

# 白艾莉 Alice：心动伴侣可复用设计对照

日期：2026-09-18。对照本地版本：`cb6f5e5`。

## 范围与判断

研究对象是洛小山／米羊的[白艾莉 Alice](https://alice.miyang.cn/)，公开资料为 [Alice_methodology](https://github.com/itshen/Alice_methodology)。本次阅读官方方法论文档并静态核查心动伴侣代码，没有安装、运行或验证 Alice 客户端，也没有修改本项目运行逻辑。该仓库公开的是方法论，不能据此声称已获得完整产品源码。

关键假设：用户希望把共性设计用于当前心动伴侣；本轮交付调研和实施建议，尚未决定功能范围。

最值得迁移的方向：让角色保持可辨认的身份，并用真实的共同经历改变之后的相处。助手与伴侣都依赖连续性，但前者主要累积工作默契，后者主要累积相处默契。

## 可迁移的机制

| 机制 | Alice 公开设计 | 心动伴侣的迁移建议 |
| --- | --- | --- |
| 稳定身份 | 设定集、受保护人格区、独立的可变偏好区 | 创作者维护角色核心；自动学习仅更新相处习惯。正常的角色编辑仍允许用户修改身份 |
| 分工明确的记忆 | 上下文与长期记忆分开；不同信息采用不同注入方式 | 区分稳定偏好、共同事件、待兑现约定；结合当前话题召回 |
| 有边界的成长 | 反思只改允许范围，变更可以回退；进化提案先呈现再执行 | 学会“难过时先听、不急着提建议”，保留来源、变更记录和撤销能力 |
| 轻量的人情味 | 正式回应之外有转场旁白 | 陪伴对话保留自然小动作或短旁白，低频出现；不要每次套同一动作 |

来源：[活人感设计](https://github.com/itshen/Alice_methodology/blob/main/chapters/16-alive-agent.md)、[上下文与记忆](https://github.com/itshen/Alice_methodology/blob/main/chapters/05-context-memory.md)、[提示词工程](https://github.com/itshen/Alice_methodology/blob/main/chapters/14-prompts.md)、[自我进化](https://github.com/itshen/Alice_methodology/blob/main/chapters/10-self-evolution.md)。上表是对公开设计的归纳及本项目建议，不代表运行效果已经验证。

## 当前项目已有基础与具体缺口

1. **人设已经相当丰富。** `src/services/characterPromptArchitectureService.ts` 包含场景、语气、不同心情的表现、示例对话和关键词触发的背景信息。优先检验这些设定在长对话中的一致性，再考虑增加背景篇幅。
2. **记忆已有用户控制和来源字段。** `src/types/index.ts` 定义来源消息、置信度及 active／locked／superseded 状态；`chatStore.ts` 支持编辑和删除。`ChatScreen.tsx` 在角色回复后调用长期记忆判断。可以沿用这些基础，避免另建一套不兼容的存储。
3. **记忆召回以新旧为主。** `src/services/aiService.ts` 的 `buildSystemMessage` 在非全量模式使用 `activeMemories.slice(-8)`。较早的重要约定、锁定记忆也可能不进入上下文。建议改为预算内的相关性选择，并优先覆盖用户明确要求长期遵守的偏好；首版可用标签、关键词、重要度和时间，不急于接向量库。
4. **长期保存存在硬截断。** `src/store/chatStore.ts` 的 `addMemory` 使用 `.slice(-100)`，没有单独保护 locked 条目；关系事件也有 100 条限制。它会从当前角色的对应列表移除早期条目。是否还可从其他备份恢复需要另外审计，不能直接认定已经不可恢复。检索窗口限制应与永久保存分离。
5. **主动开场缺少共同经历。** `generateDailyGreeting` 调用 `buildSystemMessage` 时使用 `DISABLED_MEMORY_CONFIG` 和空历史；通知服务使用预写文案。可先在用户主动进入聊天时，按授权与时间召回一个未完成约定，验证自然程度，再考虑系统通知。
6. **日记已有事实底座。** `diaryService.ts` 从实际消息摘取内容，空白日不编造经历。以后可增加带来源的角色视角总结，但不能把生成的旁白重新当作真实发生过的共同事件。
7. **人设版本可以复用。** `characterVersionService.ts` 将角色定义快照与运行中的角色数据分开。未来的相处习惯应单独版本化，撤销习惯不应回退或覆盖聊天、日记和记忆。

以上均为当前代码静态观察，尚未进行设备或模型行为测试。

## 建议的第一轮：让一句话在后来的相处里生效

示例输入：用户说“我心情不好的时候，先听我说，别急着给建议。”

预期链路：记录这条明确偏好及来源 → 按现有记忆设置保存／确认 → 多轮或重启后遇到相关场景时召回 → 角色保持自己的语气，调整回应方式 → 用户能修正或撤销。

示例输出，仅用于说明目标：

> 鹿芽：“诶，今天像是有点难熬。我先听你说，你想吐槽哪一段？”

这里要验收的是行为变化；不要求模型背出固定台词，也不要求反复声明“我记得你”。

实施顺序：

1. 审计长期记忆与关系事件的保存上限，制定保留／归档与兼容方案。
2. 给现有记忆增加只读的选择层，替换“最近 8 条”的单一策略；保留原始存储和旧记录可读性。
3. 让主聊天和进入聊天时的问候共用同一份已确认事实与偏好。
4. 有实际收益后，再引入低频的相处习惯提案及独立撤销机制。

不建议首轮引入：自动改应用代码、完整桌面工具权限、大量人格化子 Agent、照搬五层存储体系。这些能力目前没有直接服务于上述验收目标。角色自身的虚构日常若后续加入，应明确归入角色设定，与用户真实经历分开。

## 9. 建议外部讨论交回的结论格式
