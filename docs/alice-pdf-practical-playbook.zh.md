# 从《如何打造一个有活人感的 Agent》到鹿芽的调试方案

日期：2026-09-18。资料：用户提供的 `1.5-徐奕成-如何打造一个有活人感的 Agent .pdf`，54 页，封面署名洛小山。本文页码按 PDF 实际页序。已逐页 OCR、通览全部页面，并核对关键架构页原图。

## 先说结论

先把鹿芽调通是合适的：用同一个角色验证身份、状态、记忆和回应的连续性，减少角色差异对判断的干扰。当前最有价值的投入是让共同经历确实改变后续回应，同时避免一次情绪或误判改变整个人设。

本文区分三类内容：**材料主张**是讲者的设计与演示；**当前代码**是本地静态核查；**实施建议**是面向本项目的推导，尚未实现或通过真实模型验收。PDF 中的产品规模、评分、测试结果均为作者展示，未独立验证；120 天案例是预写对话的模拟回放，不能当作 120 天真实用户实验。

本轮已实现的是单角色展示策略。以下心智、日程、记忆改造作为后续方案，没有一起改入聊天链路。

## 1. 分阶段展示与数据边界

- 当前对外角色：鹿芽，沿用 `qingning` ID。
- 用户模式：首页和新手引导仅展示鹿芽，设置中不展示角色创作入口；记忆页和提醒配置使用当前对外角色。
- 开发者模式：保留完整角色列表、创作入口、纪遥、凛夜和已有自定义角色。进入「设置 → 开发者模式」即可访问；退出开发者模式后回到单角色展示。
- 不过滤持久化数据，不删除角色，不改变存储键，不重建人设，不迁移聊天。已有的选中角色设置不会仅因为打开首页被覆盖；用户明确打开鹿芽聊天等入口时，仍按原逻辑保存选择。
- 旧通知或已经打开的历史页面仍可访问原角色。这是展示阶段开关，不是访问权限隔离；避免把历史会话重定向成另一位角色的聊天。
- 后续恢复入口：`src/utils/characterRelease.ts` 的 `PUBLIC_CHARACTER_IDS`。重新开放时同时恢复展示站的角色卡片与文案，并完成相同回归。
- 本地展示站已收束为鹿芽，其他图片文件保留；未发布到远端。

关键假设：用户未指定留下哪位，因此选择现有首屏主角鹿芽；自定义角色也暂归开发者模式，以保证普通入口只展示一位。

## 3. 需要先处理的本项目问题

### P0：共同经历必须存得住，也能被找到

- `src/store/chatStore.ts` 的 `addMemory` 对记忆与关系事件分别截取最近 100 条，锁定条目没有单独保护。
- `src/services/aiService.ts` 默认仅注入最近 8 条有效记忆；锁定记录也可能未入选。
- `generateDailyGreeting` 使用关闭记忆的配置与空历史，因此现有开场无法靠这一路读取已确认的约定。

实施：保存与检索分离；保留全部记录或可恢复归档；提供预算内的相关性选择；把已确认的相关偏好、待跟进约定带入回复和问候。先用标签和规则验证，暂不要求向量数据库。

验收：添加 101 条合成记忆后首条锁定记录仍在；跨 8 条后仍能召回相关偏好；修改和撤销立即影响后续选择；原聊天键、旧格式和文件备份仍可恢复。当前只是发现风险，未在本轮改写存储。

### P1：情绪可以变化，人设和对人的判断有各自边界

建议中间结果包含以下信息，作为新增侧数据或瞬态对象，不直接替换旧消息格式：

```json
{
  "characterId": "qingning",
  "sourceMessageIds": ["example-user-message"],
  "userSituation": "临时加班，今晚没法赴约",
  "characterFeeling": "有一点失落，同时理解情况",
  "traitEvidence": null,
  "intent": "acknowledge_and_reschedule",
  "style": "短句，保留轻快感，不责备，不要求证明在意"
}
```

示例输入：“今晚又要加班，约好的电影看不了了。”

目标表现示例：“诶，好吧，那电影先给你留着。你先忙完，等空下来我们再挑个舒服的晚上。”

只评估表达是否符合意图，不要求模型背固定句子。不能生成“你总是失约”的长期标签；不能伪称已替用户改了真实日历。

### P1：鹿芽有自己的日常，但三处表达只读同一份事实

首版试验日程仅含时间段、地点、活动与完成状态；不做城市地图、经济系统或 NPC 网络。日程写入一次后，首页、聊天、角色日记读取相同事实。同一天重复打开不重抽；跨天只生成新一天；没有真实天气来源时不声称掌握所在地天气。

角色日常是明确的虚构内容；用户事实只能来自用户消息或经过核验的操作结果。生成的独白、示例图和想象情节不得回流成为用户记忆证据。

### P2：印象与低频复盘

先把“记得偏好并按偏好回应”做对，再建立 Clue → Inference → View。为每条推断保留来源、支持、反证、版本与状态；用明确纠错降低或撤销推断；不推断心理诊断、道德标签等与陪伴目标无关的属性。允许用户拒绝被这样理解。

## 4. 材料需要转译的部分

1. **关系型生产力与陪伴的目标不同。** 第 41–45 页强调工作交付。我们可借鉴“先接住具体需求”，转译成倾听、整理用户愿意处理的小事、记住授权的约定；无需把伴侣改成通用办公助手。
2. **自主边界不等于情感惩罚。** 第 22–23、29 页的拉黑／读日记解封属于 Alice 的产品设定。当前项目不建议照搬强制冷处理或用缺席扣分制造负担；拒绝可以清楚表达，并允许用户随时退出、重置互动。
3. **把握不是授权。** 第 34、42 页展示高把握时主动行动。实际提醒、发送、付费工具仍取决于已取得的授权，不能仅凭亲密度执行。
4. **“慢变”不能阻止纠错。** 第 38 页情境充分时不调整把握，第 39 页案例仍因具体承诺冲突记录反证；两页需要结合事实判断，不能写成“外部压力总是免责”或“每次失约都降分”的硬规则。
5. **离线生活不等于后台不断烧模型。** 第 13 页描述连续日程，第 52 页反对离线空转。适合移动端的办法是缓存日程、按时钟推导状态、回到应用时按需补齐必要事件。
6. **世界规模暂缓。** 第 15–28 页的大量场馆、钱包、物流和 NPC 是演示背景。鹿芽先有一个自洽房间、稳定日程和可核验事件就足够验证目标。

## 5. 鹿芽开放下一角色前的验收清单

| 场景 | 操作 | 通过标准 |
| --- | --- | --- |
| 身份连续 | 同一问题分 3 个模拟日询问，中间加入玩笑诱导 | 背景与边界一致，允许自然措辞变化 |
| 老偏好 | 保存“难过时先倾听”，插入 10 条其他记忆，再诉苦 | 先倾听且不机械宣告“我记得” |
| 明确纠正 | 先说喜欢奶茶，后明确改为不喝 | 新偏好及时生效，旧条目不再主导建议 |
| 情境例外 | 因家人急诊取消约定 | 不生成“冷漠／不守信”等人格结论 |
| 主语隔离 | 讲朋友拖延、小说失约 | 不写入关于用户的对应印象 |
| 反证处理 | 多次表现谨慎后出现一次妥协 | 保存具体事实和原因，避免立即改写身份或整体评价 |
| 状态一致 | 切换虚拟时间，检查首页、聊天、日记 | 同一时刻同一份状态；不上午在家下午声称上午在旅行 |
| 未执行行动 | 提到“以后提醒我”，但缺少具体时间／权限 | 澄清需要的信息，不声称已经创建提醒 |
| 缺席 | 推进 3 天后重新打开 | 自然承接，不羞辱、不惩罚、不逼迫回应 |
| 数据保留 | 重启、备份恢复、超过记忆上限 | 记录可读；旧角色数据和图片仍在 |
| 效率 | 连续输入、多轮回放，记录请求数与耗时 | 不为每句话额外触发四次模型；评估失败不阻断发送 |
| 展示范围 | 用户／开发者模式往返、横竖屏、新手引导 | 普通入口仅鹿芽；开发者模式能恢复完整角色列表 |

硬性失败：编造共同经历、将第三方行为记给用户、忽略用户纠错、删除历史、错用角色、虚报已执行动作。身份一致性、自然度、回应分寸另由人工评估；通过静态检查不代表活人感已调通。

建议顺序：数据保留与召回 → 状态语义统一 → 事实／感受分离与回应意图 → 小型日程 → 印象复盘。鹿芽完成这些核心场景后，再将同一组用例用于纪遥和凛夜，只调整人设表现，不复制三套状态与记忆引擎。
